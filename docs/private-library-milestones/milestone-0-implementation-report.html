What changed,
and why.

M0 did not build the library. It made one promise executable: before the node stores a job, the phone and node must agree exactly on its owner, identity, state, and wire format.

Start with the system

PhoneSends requests and validates replies.
RelayRoutes frames between phone and node.
NodeAuthenticates the phone and will own durable jobs.

There are two protocols, not one:

relay envelope v1
└── application message v2

This separation matters: Cantor can change job semantics without changing how the relay routes bytes.

1. Ownership is now safe

The danger: if job.create accepted an owner field, a client could ask the node to create a job for somebody else.

The rule: requests contain no trusted owner. After signature verification, the node derives:

principal_id = SHA-256(canonical 32-byte Ed25519 public key)

Typed handlers receive that authenticated context. Ownership therefore comes from cryptographic proof, not JSON.

Code → AuthenticatedSession and typed dispatch · session.rs

2. Retries can be made durable

Three IDs solve three different problems:

IDMeaning
idOne network attempt. Matches a reply to a pending request.
client_request_idOne intended creation across reconnects. M1 will use it to prevent duplicates.
job.idThe node's permanent identity for the accepted job.

The app now ignores responses whose request ID is no longer pending.

Code → pending request correlation · connection.ts

3. Jobs are no longer arbitrary strings

State, generation stage, progress unit, and errors are strict enums. A job also carries a monotonic revision.

state: queued | preparing | running | ... | completed | failed
stage: plan | codes | diffuse | decode
revision: 1, 2, 3, ...

The app accepts job.updated only when its revision is newer. Timestamps remain useful for display, but revisions decide ordering because clocks can move.

4. The network boundary is real now

Generated TypeScript does not validate runtime data. WebSocket JSON arrives as unknown, so the app now checks it before creating trusted objects.

5. Node capabilities are explicit

NodeInfo now reports structured installed models, limits, live load, and feature flags. The app does not guess support from “v2”.

model: { selector, family, engine }
limits: { duration, caption bytes, lyrics bytes, page size, queue size }
features: { jobs_create, library_list, secure_tunnel, ... }

M0 advertises later features as false. Job mutations return feature_unavailable; there is still no database or queue.

Code → structured NodeInfo · relay.rs

What was deliberately not built

  • No SQLite job store.
  • No scheduler or generation mutation.
  • No library UI.
  • No pause/resume/cancel contract.
  • No end-to-end encryption yet.
Recommended next step: implement the authenticated encrypted tunnel as M0.5, then send private prompts and lyrics in M1.
