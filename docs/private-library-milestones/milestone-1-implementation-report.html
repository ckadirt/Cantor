A submit is now
a durable fact.

M1 makes one guarantee: if the phone sees “Queued,” the request already exists on the node's disk—and retrying cannot create a duplicate.

The whole idea

1 · PhoneFreezes request and persists its UUID.
2 · NodeValidates, fsyncs files, commits SQLite.
3 · ReplyReturns the node's permanent job ID.
persist locally → send → fsync sidecars → COMMIT → acknowledge

The ordering is the feature. A network reply is never evidence for data that only existed in RAM.

Why retries produce one job

The uniqueness key is (authenticated principal, client_request_id). The node also hashes the normalized model + generation request.

What the node findsResult
No existing keyCreate one UUIDv7 job.
Same key + same hashReturn the existing job ID.
Same key + different hashidempotency_conflict; mutate nothing.

This lookup runs before queue and disk checks. Even a newly full queue cannot block recovery of an earlier acceptance.

The phone has an outbox, not hope

draft ──tap──▶ pending ──job.accepted──▶ accepted
                     └──terminal error──▶ rejected
  • pending is persisted before the WebSocket send.
  • Timeout/reconnect/relaunch resends the same UUID and frozen bytes.
  • Only a non-retryable node error becomes rejected.
  • A synchronous guard prevents two taps creating two intentions.

Admission is cheap and explicit

Before creating files, the node checks UUID/field bounds, exact installed model, per-principal queue capacity, and its free-space reserve.

[jobs]
max_queued_per_principal = 20
minimum_free_bytes = 2147483648

The same configured queue limit is advertised to the phone. After acceptance, the node pushes a refreshed aggregate queue count.

Failure policy

Failure pointSafe outcome
Before database commitNo acknowledgement; recognizable orphan is removed, unknown content quarantined.
After commit, before replyRetry returns the committed job.
Another identity lists/gets itnot_found / empty page; every query includes principal.
Privacy boundary: durable and private-by-owner does not mean encrypted-in-transit. The relay carrier can still read prompt JSON until the secure-tunnel milestone.

What M1 does not do

No scheduler consumes the queue. No model loads, progress, audio, pause, or cancellation occurs. The node truthfully advertises max_concurrent_jobs: 0 and execution_starts_in_m2.
