Why two workers cannot race

The claim is one immediate SQLite transaction. It refuses a second claim while any job is active, increments the attempt, and returns an owned work item. Inference then runs without holding node state or SQLite.

UPDATE … WHERE state='queued' AND NOT EXISTS(active job)
worker update … WHERE id=? AND attempt=?

The attempt is a token: an old callback cannot mutate a recovered job.

Stage changes and endings persist immediately; ordinary callbacks persist at most once a second. Every saved update increments a revision. The app accepts only a higher revision, so reconnect/list/push races cannot roll backward.

“Completed” has a strict meaning

  1. Write a random temp WAV inside the job.
  2. Flush, fsync, parse the PCM header, check frames, hash SHA-256.
  3. Rename to master.wav and fsync its directory.
  4. Replace job-root manifest.json with schema 2.
  5. Index the artifact and only then transition to completed.

A restart adopts a valid renamed master. It also repairs a stale manifest—but only after the indexed WAV passes digest verification. Interrupted inference restarts from the immutable request, with three claims maximum.

User controls stay authoritative

The engine may enrich a caption during planning. It may not replace explicit lyrics, duration, steps, CFG, or seed. The adapter reasserts those accepted fields after planning and rejects an expanded duration before expensive diffusion.

Privacy and CLI

job.updated goes only to sessions whose authenticated principal owns it. Other users may see aggregate load, never model/title/job details. cantor generate now submits through this same queue; -o copies the verified master after completion and Ctrl-C merely detaches.
