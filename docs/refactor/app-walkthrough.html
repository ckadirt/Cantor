1The shape of the app

App.tsx ── identity boot (keychain) ──► Onboarding  or  FieldScreen
                                                        │
  useBackendRuntime (network, cache, audio files) ──────┤  "data"
  buildFieldController  → entities + presentations      │
  layoutField           → groups + placements           │  "geometry"
  useFieldCamera        → camera, level, focus, re-cuts │  "navigation"
  FieldCanvas (Skia)    → draws everything that moves   │  "picture"
  FieldOverlay, SongSurface, Curtains, sheets (RN views)│  "chrome"

After onboarding there is only one screen, FieldScreen. There's no navigator. Zooming is the navigation: the map (L0), a shelf of rows (L1), the player (L2) and the grain/waveform (L3) are all the same drawing seen from different camera distances. The composer, engines, song sheet and job sheet are “curtains” pulled down or up over it.

Everything runs on three threads:

JS threadReact, your state, the network, decoding. Slow and bursty.
UI threadReanimated worklets (functions marked 'worklet') and gestures. They run every frame.
Render / GPUWhere Skia actually paints the pixels.
Almost every flicker comment in the code comes down to “two of these threads disagreed for one frame.”

2What Skia is

Skia isn't a component. It's the 2D graphics engine that Chrome, Flutter and Android itself use to draw pixels. @shopify/react-native-skia exposes it to React Native in two ways:

  1. <Canvas> is a component. It's one native view with its own GPU surface. Its children (<Fill>, <Path>, <Picture>, <Group>) aren't RN views. They're a scene graph reconciled by a separate React root inside the canvas. That separate root is why “a React commit is not proof Skia painted” (the Flicker Law).
  2. SkPicture is a recorded list of draw commands (“move here, fill this path, draw this text”). You record it once and replay it cheaply.

The field uses a pattern that matters for everything else:

const facePicture = useDerivedValue(() =>
  createPicture(canvas => drawFieldFaces(canvas, faceFlights, …, cameraShared, …)));

features/field/FieldCanvas.tsx:2991

This is an imperative drawing function running on the UI thread. It re-records the whole field whenever any shared value it reads changes. React is out of the loop: at L0, a pan never touches JS for drawing. It's the right architecture, and it's why the map feels smooth.

Two render paths inside FieldCanvas

PathWhere it recordsUsed for
Native — NativeFieldContentUI thread, per frameL0 to L2
Recorded fallback — recordFieldPictureJS thread, inside a useMemograin distance, and whenever nativeField is false

nativeField is a 10-condition boolean at FieldCanvas.tsx:722: fonts loaded, flights resolvable, both ends of the re-cut native-drawable, and so on. Several documented bugs were “the field silently fell back to the picture path” (see the lastVisualPlacements trap in hacking-app.md).

Canvas count: the field has 2 (songs, plus a transparent one for jobs). Every MorphText, Dial and control-state glyph in the chrome is its own <Canvas>, so its own GPU surface.

3State: what exists and where it lives

What's in React state today

  • useBackendRuntime (runtime/useBackendRuntime.ts): backends, snapshots (the per-node songs and jobs), localAudio (per-song file state), downloading, outbox, pairing, storageError.
  • FieldScreen: about 30 useStates. There are sheet open/target flags (×4 sheets), lens, arrangement, order, seed, date resolution, grain, analyses, budget, after-song mode, song/job errors and busy flags, the viewport, visualPosition, nowMs and more.
  • useFieldCamera: camera (a React mirror of the real camera), focusKey, playerKey, recutClock, descentTicket. Plus about 15 shared values: the real camera, the pull, the flight, the seats.

The derivation chain

Recomputed with useMemo:

snapshots + localAudio + backends + outbox
  → buildFieldController   (new FieldPresentation object for every song)
  → layoutField            (groups, placements)
  → useFieldCamera re-cut  (only if layoutsDiffer → generation++, flights from→to)
  → FieldCanvas            (faces, rows, labels rebuilt per re-cut)

Is it efficient?

The UI-thread part mostly is. React is doing a lot more work than it looks like. These four costs are what I'd blame first for heat and small glitches.

cost 1 · JS · during every gesture

Camera mirroring re-renders the whole screen

Each pan, pinch or flight frame calls runOnJS(mirrorCamera) → setCameraState in useFieldCamera.ts:394. mirrorBusy throttles it to one in flight, but that still means “as fast as JS can commit”, all gesture long. Every commit re-runs FieldScreen's ~1900-line body, FieldCanvas, the overlay, SongSurface, the a11y list and the origin mark. The mirror exists because level, hit-testing, songAlpha and chrome read the camera from React.

cost 2 · JS + UI · the whole time music plays

Playback keeps the screen re-rendering ~6×/s and redraws the field every frame

  • setVisualPosition runs every 160 ms while playing (FieldScreen.tsx:734) just to feed playingProgress to the fallback picture. That re-renders all of FieldScreen, even with the phone sitting on the map.
  • facePicture reads positionSeconds.value, which is a withTiming running for the whole song. So every face in the field is re-recorded every frame for as long as music plays, even at L0 with nothing moving. heldFocus keeps the last player focused, so that clock stays attached after you zoom out.

This is very likely a real part of the “phone gets warm” symptom.

cost 3 · bridge · on every snapshot change

Any snapshot change asks native storage about every song

The effect at useBackendRuntime.ts:895 depends on snapshots. A job-progress event, a sync page or a rename all trigger audioStore.inspect on every song on every node over the bridge. Then setLocalAudio returns a fresh object even if nothing changed, which rebuilds the controller. With 30 songs you don't notice. With 500 songs and a generation running, it's a steady storm.

cost 4 · JS · on every data change

The controller never shares structure

Every rebuild creates new presentation objects for every song. FieldCanvas then has to compare them field by field to get the old map back (FieldCanvas.tsx:551), so the Skia mappers don't restart. That's a patch for a problem one layer up. The same pattern repeats: lastVisualPlacements, heldFocus, previousPresentations, and “held by ref because the Jest mock isn't stable”.

The structural issue is ownership. FieldScreen (1938 lines) and FieldCanvas (4288 lines) own almost everything, so any change anywhere re-renders nearly everything. Correctness then depends on dozens of carefully commented identity tricks to stop those re-renders from reaching Skia. Each tricky comment is a flicker that was fixed once.

4The map

Grouping

field/layout.ts, field/arrangements/, field/browse.ts

  • An arrangement (by date at week or month resolution, or by playlist tag p/<name>) turns entities into groups. Date groups start newest first.
  • Groups sit on a 2-column grid, SHELF_GAP_WORLD = 300 apart. Inside a group, members are seated by order (time, duration, or seeded random) into an irregular oval (“bloom”). The oval is seeded by the group key, so it's deterministic between refreshes. Denser groups compress before they grow.
  • A placement is a (song, group) pair. A song in three playlists is three marks, which is why sheetTarget carries a groupKey.
  • Each group also has a separate shelf pose: rows 92 px apart at L1. Zooming into a group “gathers” the bloom into that list.

Camera

field/camera.ts

The camera is {x, y, scale}. The level is just scale / fitScale compared against LEVEL_SCALE_RATIOS. Crossfades between representations are “bands” (REPRESENTATION_WINDOWS); positions are “arrivals” (log-scale, no easing). When the layout really changes (regroup, song added), you get a re-cut: generation+1, each placement becomes a flight from its old pose to its new one, on a born clock over 850 ms.

Is every song rendered at once?

QuestionAnswer
Iterated every recorded frame?Yes. drawFieldFaces loops over every flight and skips anything outside the viewport plus overscan (FieldCanvas.tsx:2240). Rows and labels do the same in nativeRows.ts and nativeLabels.ts.
Drawn every frame?No, only what's on screen. But at L0 overview, everything is on screen by design, so you draw all of them.
Built per re-cut?Yes, for every song, not only visible ones: face paths (cached per song), plus nativeRowModel, which lays out the title and metadata text for every row (FieldCanvas.tsx:3040), even at L0 where titles are invisible.

Can it handle hundreds?

Geometry, yes. FieldGroupLab already checks 576 songs across 24 weeks, but it's a geometry check, not a performance one. What I'd expect to hurt first as the library grows, in order:

  1. the native inspect storm (cost 3)
  2. building text for every row at the start of each re-cut, on JS, which delays the 850 ms clock
  3. whole-field re-recording every frame during playback (cost 2)
  4. controller and layout rebuilds on every progress tick (cost 4)

A few hundred faces drawn per frame on the GPU is fine. A few thousand would want per-song cached pictures or an atlas.

I haven't profiled any of this on the Xiaomi yet. These are predictions from reading the code, and measuring them should be step one.

5Why the bugs feel endless

The recurring shapes:

  • Two clocks on one gesture. React's lagging camera copy drives chrome while the UI-thread camera drives the canvas.
  • Two renderers for one field. The native and fallback paths switch on a large boolean, and anything that flips it for one frame is a seam.
  • Ownership hand-offs between React and Skia: glyphs, the player lifetime (playerKey vs focusKey), sheets that keep their subject while closing.
  • Identity churn. New objects each render force defensive memo and ref tricks downstream.

Patching them one at a time works, but each patch adds one more invariant to hold in your head. A redesign would remove the categories: one owner per value, one renderer, and a UI-thread-owned scene that React only feeds with discrete facts.

6Where this could go (not decided yet)

  1. Split state by rate.
    • Data (songs, jobs, files) goes in a store with structural sharing, updated incrementally per event.
    • Discrete UI (sheets, lens, arrangement) goes in small feature stores, not 30 useStates in one component.
    • Continuous values (camera, playhead, pulls, progress) are shared values only, never mirrored per frame.
  2. Make React camera-agnostic. Level and focus become events sent across threads when a threshold is crossed, not a mirrored camera.
  3. One renderer. Bring grain/L3 onto the native path and delete recordFieldPicture, or give both paths a single draw function.
  4. Draw only what changed. Cache a picture per song (face + row). Redraw only the player while music plays. Build row text lazily for rows that come into view.
  5. Break up the two god files along those seams: data / navigation / scene / chrome.

docs/refactor/hacking-app.md's module map is already stale (it still names MainScreen and LibraryTimeline). It would be rewritten as part of this.

7Questions for you

  1. Where do you see the flicker most? For example: regrouping, entering or leaving a song, opening sheets, lens switches, startup hydration. Knowing the top 3 tells me which of the categories above you're actually hitting.
  2. Heat: is it worst while playing, while generating (job progress), while panning, or just sitting idle on the map? That would separate costs 1–3.
  3. Scale target: is “a few hundred songs per user” the goal, or should we design for thousands?
  4. Is L3 (grain) staying? Its being on the JS picture path is the main reason two renderers exist.
  5. Appetite: a staged refactor behind the current behaviour (measure → fix the three cheap wins → restructure stores → unify the renderer), or a bolder rewrite of FieldScreen/FieldCanvas now, before alpha?
The cheap wins are small and independent: stop the per-frame playback redraw, stop the 160 ms screen re-render, and make the inspect effect incremental. They can be profiled and fixed while the bigger design is discussed.
