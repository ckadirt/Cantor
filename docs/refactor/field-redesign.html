1The two flickers, traced

flicker A · L1 → L2 · bars pop in seconds late

The reveal is tied to the camera, not to the data

  • Analysis starts only when a song becomes focused, i.e. at the descent (FieldScreen.tsx:1225). It decodes the whole song on JS, which the code's own comment says takes “several seconds for a two-minute song”.
  • The results live in an in-memory AnalysisCache only, so every app launch decodes again, and so does every song opened after a restart.
  • The circle's bars reveal on drawn, a clock started by the camera phase (NativeSongDetail, FieldCanvas.tsx:2758). If the data isn't there yet, drawn runs 0→1 over nothing. When the analysis lands later, the model prop changes and the bars appear already at drawn = 1: a pop.
  • The seal already has the fix: soundClock is born at 0 when a measurement arrives while you're looking. The circle never got it.

Category: content that arrives late has no clock of its own.

flicker B · L2 → L1 · name vanishes one frame on arrival

Ownership of one glyph is handed between two Skia nodes through React

  • While in a song, the row batch excludes the focused placement (rows memo, FieldCanvas.tsx:3040). The name is drawn by the player's own NativePlacementFlight instead.
  • When the ascent lands, mirrorCamera calls setPlayerKey(null) (useFieldCamera.ts:410). In that one React commit:
    • the player flight unmounts from the Skia tree (the name's owner leaves), and
    • rows gets a new array that includes the row again. But rowsPicture is a useDerivedValue, so its mapper is re-created in a passive effect, one step later.
  • For one frame, nobody draws the name. This is exactly the gap that “house rule 5” and Flicker Law rule 4 warn about, happening at the one hand-off that still goes through React.

Category: who draws a thing is decided by a React commit, while when it's drawn is decided by the UI thread.

Traced from the code; I'll confirm both on the Xiaomi with burst capture before and after.

Every other flicker I found in the code comments falls into one of these two categories, or into the “two render paths” one from the walkthrough. So the design removes those three categories instead of the individual bugs.

  • Empty field after a regroup. In the lab, switching scenario while the camera was far away (the regroup and the flight home on one tap) settled on an empty canvas while React's camera read home. FIT MAP recovered it. Same category as flicker B: two copies of the camera disagreeing.

2The rule the design follows

React decides what exists. The UI thread decides who draws it, where, and how much.

  1. One renderer. One canvas, one draw function, one frame state. No native/fallback switch, no per-flight React components, no second canvas for jobs.
  2. Ownership is a UI-thread value. “Which placement is the player” and “has it shrunk back into its row” are numbers in the frame state, not React state. The row and the player are the same slot drawn in two poses, so there's never a hand-off.
  3. Every arrival has its own clock. Data landing (analysis, download, title rename, a new song) starts a born clock in the scene. Nothing appears at full ink because the camera already got there.
  4. Nothing per-frame goes through React. The camera, playhead, pulls and progress are shared values. React hears about threshold crossings (level changed, focus changed), never frames.
  5. Draw only what changed. The settled field is a cached picture; motion and the player are drawn live on top.

2½What the next features need

Three features change what the design has to carry: importing your own songs (before alpha), then a semantic field (node-side embeddings projected with UMAP) and more lenses (tree and others, with a smooth player). Today the code assumes the opposite of each:

Today's assumptionWhere it's baked inWhat it becomes
Every song comes from a node entity key nodePubkey:songId; FieldPresentation.backend required; AudioRef = (nodeKey, songId, digest); unpaired nodes' songs dropped unless pinned A song has a source: node or device. Keys become node:<pubkey>:<id> / device:<contentHash>. Playback, analysis and lenses only see a SongRef + a way to open its audio.
The field is groups on a grid layoutField, Group, bloom ovals, shelf seats Split into two steps: a placer gives each song world coordinates (grid-of-groups today, UMAP coordinates for the semantic field). Grouping becomes optional, and clusters can be derived for labels and shelves. The scene only ever sees target arrays, so switching date → semantic is an ordinary re-cut.
Exactly two lenses drawFieldFaces blends circle↔seal on one lensMix; seal code threaded through the player, ring and seek A lens contract the renderer calls: identity(song), sound(analysis), draw at mark/row/player poses, hit/seek at the player. Lens change is (from, to, t), with a generic scale-out/scale-in morph and optional hand-written pair morphs (circle→seal keeps its dot walk).
Identity = the recipe (seed, model) AGENTS.md two-layer rule; facePoints inputs Identity = a fingerprint: the recipe for generated songs, something derived for imported ones (see the questions). The rule survives: identity must exist at L0 without the audio being measured.
Analysis is a detail for one song decoded on descent, in memory An analysis store is core infrastructure: persisted per artifact, filled by a background queue with priority (focused → on screen → rest), throttled for heat. Every lens's sound layer and the player read it.

None of this fights the redesign; it sharpens it. The scene already takes typed target arrays (so any placer works), the owner slot already makes the player one drawing (so any lens can morph through it), and the stores already separate data from drawing (so a second source is one more producer). Thousands of songs also stops being hypothetical: 300 imported songs on day one.

Songs, homes and copies

Import from the phone, import on the node, offload to a node and bring back all fit in one model:

Song      id · kind (generated | imported) · title · artist · album · track
          · duration · recipe? (generated only) · tags (playlists = p/<name>)
Home      where the song's record is the truth: device | node:<pubkey>
Copies    device original (content URI, never evicted) · node artifact
          · phone cache (remote / partial / cached / pinned, as today)
Features  small derived data, arrives later: analysis summary, embedding, UMAP xy
  • Import on the phone creates a song with home = device and a device-original copy. The metadata comes from the file's tags.
  • Offload uploads the file, metadata and tags to a node, moves the home there, and then (optionally) deletes the original. Android shows its own confirmation for that.
  • Bring back is today's download/pin, unchanged.
  • Import on the node is the same song with home = node from the start.
  • Playlists: tags live with the song's home. Device-home songs keep them in the phone database; node-home songs keep them on the node, as today. A playlist is still derived from all songs' tags, so one playlist can mix both. Offloading moves the tags with the song.
  • L0 stays cheap: identity comes from a fingerprint (recipe, or a hash of the metadata). Features are a per-song row that arrives later from the node and enters with its own clock. What an imported mark should look like is still open. The architecture only guarantees it can use either.

Two consequences.

  1. A real phone database. The whole library cache is one AsyncStorage JSON blob today (cantor.private-library.v1), rewritten whole on every commit. With thousands of songs plus metadata and features, that should become SQLite, with a one-time migration from the old key. Storage keys are a compatibility contract, so the old blob must keep loading.
  2. A wire change for offload and node-side import. SongHeader requires model and has no artist or album. Imported songs on a node need an optional kind and metadata, plus an upload path. That touches protocol/, the node, and the fixtures. Phone-only import needs none of it.

What each layer replaces

The runtime's network side (BackendConnection, secure tunnel, sync reducer, outbox, repositories) stays as it is. Only the React state it publishes into changes. Storage keys and stored shapes don't change.

4The scene: one renderer

Frame state (UI thread)

type Frame = {
  camera: Camera;                  // authored by gestures, as today
  recut:  { from: Targets; to: Targets; clock: number };
  owner:  { slot: number; pose: number };   // player slot, 0 = row … 1 = player
  lens:   number;                  // 0 circle … 1 seal (existing LENS_MORPH clock)
  arrivals: Float32Array;          // per slot: 0 → 1 born when data lands
  playhead: number;                // seconds, the player's visual clock
  grain:  GrainBars | null;        // L3
};

Drawing

drawField(canvas, frame):
  layer 1  settled marks + labels   → cached SkPicture, replayed with a transform
                                       (re-recorded only when the set or lens band changes)
  layer 2  moving slots             → drawn live: re-cut flights, gather/bloom, arrivals
  layer 3  the owner slot           → face ⇄ row ⇄ player by owner.pose, name morph, ring, detail
  layer 4  playhead + progress      → only this layer reads the playhead
  layer 5  grain (L3)               → same camera, same frame
  layer 6  veils
  • Flicker B goes away by construction. The row and the player are one slot. Ascending just runs owner.pose 1→0 on the UI thread. When it reaches 0, that slot is simply drawn as a row by the same function in the same frame. React is told afterwards, as an event.
  • Flicker A goes away by construction. The detail's ink is min(cameraPhase, arrivals[slot]). Data landing late starts arrivals[slot] at 0 and it draws in. Analysis also starts earlier (when the song enters the shelf you're in, or right after download), and it's persisted, so usually it's already there.
  • Playback no longer re-records the field. Only layer 4 reads the playhead.
  • L3 is just layer 5. It isn't a second renderer, so adding it is ordinary work, not a special case.

Implementation primitives

  • One <Canvas> with one <Picture picture={frameRecording}/> child, where frameRecording is a useDerivedValue that calls drawField. The Skia React tree never changes shape after mount, so there are no reconciler commits during navigation.
  • Inputs from JS reach the worklet through shared values set in one batch per re-cut, never through closure capture. That's what removes the “mapper re-created one step later” class.
  • The existing pure geometry (camera.ts, bands.ts, layout.ts, seal.ts, songPose.ts, labelMorph.ts, the motion engine) is reused. This is a new owner for that code, not new geometry.

For thousands, the L0 overview also needs a level-of-detail rule. Below a screen-size threshold a mark is drawn as a dot, not its full face path. That's a band like the others, and it's cheap.

6Heat budget

A target we can measure against on the Xiaomi:

  • Idle on the map, music playing: JS thread ~0% (no timers re-rendering), UI thread drawing one small layer.
  • Panning: zero React commits per frame. JS only hears about level crossings.
  • Generating: job progress repaints one mark, and nothing else rebuilds.
  • Each song decoded at most once per install for analysis.

7Migration plan

A bold rewrite of the field, done so the app works at every step.

  1. Measure. Extend FieldGroupLab with 2,000 songs; add a debug overlay showing JS and UI frame rate and React commits per second. Take a baseline on the Xiaomi and record flickers A and B with burst capture. ~½ day
  2. Stores. libraryStore keyed by source from day one (only node filled in yet), with incremental updates and incremental inspect; analysisStore with the background queue; persisted analysis started early; uiStore and playbackStore; FieldScreen reads selectors. This fixes most of the heat on its own and is independent of the renderer. ~2 days
  3. Scene renderer, built beside the current one behind a flag, in features/scene/: frame state, typed targets, the owner slot, arrivals, cached settled layer, and the lens contract, with circle and seal ported onto it as its first two lenses. It reaches parity with the lab and on device (marks, rows, player, both lenses, jobs, re-cuts, gather). the big one, ~1 week
  4. Switch over. Replace the camera mirror with events; move chrome fades onto shared values; delete NativeFieldContent, recordFieldPicture and the flight components. ~2 days
  5. Import on the new foundations: a device source in libraryStore, a media-library picker, playback from a content URI, and fingerprint identity. Because stores, analysis and lenses already speak SongRef, this is mostly a new producer plus the import UI. ~3–4 days, depends on the answers below
  6. L3 as layer 5, if we want it for alpha. ~2–3 days
  7. After alpha: the semantic placer (UMAP coordinates from the node as a new placer) and new lenses (tree, …) against the lens contract. Neither should touch the renderer.
  8. Docs. Rewrite hacking-app.md and the parts of AGENTS.md that describe the old owners. The Flicker Law stays, and the redesign is how we obey it.

Estimates are rough. Phase 3 carries almost all the risk. Phase 2 pays off even if phase 3 slips.

8Decisions for you

About import (these shape the data model)

  1. Where do imported files live? Referenced in place through Android's media library (recommended: 300 songs can be gigabytes), or copied into Cantor's storage?
  2. What is an imported song's identity? A fingerprint that exists at L0 without decoding: a hash of the file or of title/artist/duration used as a pseudo-seed (recommended, instant, and stable), or something derived from the audio (more meaningful, but it needs every song decoded before its mark can be drawn)?
  3. Do imported songs ever reach a node? The semantic field computes embeddings on the node, so either the audio is uploaded to a node (bandwidth, and your own music leaves the phone even if encrypted), or the phone runs the embedding model, or imported songs are only on the date/playlist fields.
  4. Playlists and tags for imported songs are on the node today (p/<name> tags). For device songs they'd be stored locally, unless they sync to a node. Is local-only fine for alpha?

About the plan

  1. Store library: a small hand-rolled store on useSyncExternalStore (recommended: no dependency, ~100 lines, easy to test in Jest), or Zustand.
  2. Order: start with phases 1–2 now (measurable, low risk, fixes heat and flicker A), then the renderer? Or go straight at the renderer?
  3. L3 for alpha: decide after phase 3 lands, when we can see how hard it actually is?
